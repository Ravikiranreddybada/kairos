# Product

## Platform

web

## Stack

React + Vite + TypeScript single-page app in `web/`, Tailwind v4. Talks to the FastAPI `/v1` API through the Vite dev proxy, which adds the `X-API-Key` header so the browser never holds a key. No backend change is needed for the UI.

## Users

Primary: a store or category planner who decides weekly purchase orders for stores × SKUs. They ask "what should I order for S01 this week, and why?" and must be able to question every number before acting.

Secondary: interviewers and reviewers who see Kairos as a portfolio piece. They judge whether the system is grounded, honest about uncertainty, and well engineered. The UI serves the planner first; the portfolio reader is served by the same truth, not by extra show.

## Product Purpose

Kairos turns probabilistic demand forecasts into inventory decisions (safety stock, reorder point, order quantity, stockout probability) and exposes them through a grounded copilot. Success: a planner gets a decision plus the evidence behind it in one place, and trusts it because every figure traces to a tool result.

## Positioning

The copilot never invents numbers. Every figure in an answer comes from a read-only tool call, a numeric grounding verifier checks the answer before it ships, and policy answers cite `source#section`. When the LLM is down, it degrades to direct tool results instead of failing.

## Operating Context

Planners work weekly, at a desk, on desktop screens, often with a spreadsheet beside them. Questions are about specific stores (S01–S04) and SKUs (SKU001–SKU012). Decisions go through a separate four-eyes approval ledger; the copilot only reads.

## Capabilities and Constraints

- First UI surface: the copilot chat (`POST /v1/agent/chat/stream`, SSE). Stream events: `node` (guard, route, cache, llm with `tools`, tools, verify, finalize) then `result` (answer, status ok/blocked/degraded/budget_exhausted, tier fast/strong, tool_calls with name/input/latency/is_error, citations, grounding score/checked/ungrounded/passed, usage, cost_usd, latency_ms, trace_id, data_version).
- Tool outputs are not in the chat result. The UI shows evidence by calling the matching read-only REST endpoint with the same inputs (forecast, policy, worklist, stress test, network, what-if, explain, model health, anomalies, proposals).
- 13 tools: get_forecast, inventory_policy, what_if_promo, explain_forecast, reorder_worklist, detect_anomalies, run_sql, simulate_supply_risk, network_pooling, model_health, decision_history, browse_docs, search_docs.
- Sessions remember stated preferences (e.g. target service level) per `session_id`.
- Forecast intervals are 80%. Stockout days are censored demand.
- Undecided: other surfaces (forecast/inventory workspace, decisions + audit, ops) come later.

## Brand Commitments

Name: Kairos. No logo or brand colors exist yet. The user requires that the UI must not look AI-generated and must avoid AI-typical colors (purple/blue gradients, neon glow, generic SaaS palettes).

## Evidence on Hand

All data is synthetic (generated by `kairos seed`), served by the local API. Real policy documents live in `src/kairos/rag/corpus/`. There are no customers, testimonials, or benchmarks to show; do not invent any.

## Product Principles

1. Evidence beside every answer: the planner sees the tool data, not only prose.
2. Uncertainty is shown, never hidden: intervals, probabilities, and grounding scores are first-class.
3. Read-only and honest: the copilot advises; humans decide elsewhere.
4. Degrade visibly: blocked, degraded, and ungrounded states are clear, not disguised.

## Accessibility & Inclusion

WCAG 2.2 AA. Keyboard-first chat. Charts carry text equivalents; never color alone for meaning.
